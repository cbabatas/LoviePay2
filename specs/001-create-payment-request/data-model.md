# Data Model: Create Payment Request

## Demo User

Represents the acting user after mock sign-in.

Fields:

- `id`: Stable identifier for comparing the user against friends and requests.
- `fullName`: Display name shown in the sidebar.
- `email`: Mock sign-in email and sender contact value.
- `password`: Mock sign-in password used only for demo entry.
- `customerNumber`: Customer number shown in the sidebar.
- `avatarLabel`: Basic avatar initials or label shown in the sidebar.
- `receiverAccounts`: List of receiver accounts owned by this demo user.

Validation rules:

- `id`, `fullName`, `email`, `customerNumber`, and `receiverAccounts` are required.
- `receiverAccounts` must include at least one account with a supported currency.

## Friend

Represents a potential recipient from the demo user's friend list.

Fields:

- `id`: Stable friend identifier.
- `fullName`: Recipient display name.
- `email`: Recipient email searchable by the user.
- `phone`: Recipient phone searchable by the user.
- `active`: Whether the friend can receive a new payment request.

Validation rules:

- Friend `id` must not equal the current demo user `id`.
- The friend list must not include the current demo user as a friend record.
- Only active friends can be selected for request submission.
- Search can match `fullName`, `email`, or `phone`.

Relationships:

- A `Payment Request` references one selected active `Friend` as recipient.

## Receiver Account

Represents a demo user account that can receive requested funds.

Fields:

- `id`: Stable account identifier.
- `label`: User-visible account label.
- `currency`: Currency derived into the created payment request.

Validation rules:

- `id`, `label`, and `currency` are required.
- Accounts without a supported currency cannot be used.
- Currency is selected only through the receiver account and cannot be manually overridden in this flow.

Relationships:

- A `Demo User` owns one or more `Receiver Account` records.
- A `Payment Request` references one selected `Receiver Account`.

## Payment Request

Represents a system-generated request for money from a selected friend. Payment request records are persisted in Supabase after backend validation succeeds.

Fields:

- `id`: Supabase record identifier.
- `senderId`: Current demo user identifier.
- `recipientId`: Selected friend identifier.
- `receiverAccountId`: Selected receiver account identifier.
- `amount`: Requested amount.
- `currency`: Currency derived from selected receiver account.
- `note`: Optional user-entered note.
- `status`: Request lifecycle state.
- `hash`: Unique public hash.
- `shareableLink`: Public link generated from the unique hash.
- `createdAt`: Creation timestamp.

Validation rules:

- `senderId` must equal the current demo user `id`.
- `recipientId` must reference an existing active friend.
- `recipientId` must not equal `senderId`.
- `receiverAccountId` must reference an existing receiver account with supported currency.
- `amount` must be greater than zero and less than 1,000,000.
- `currency` must equal the selected receiver account currency.
- `status` must be `pending` when created.
- `hash` must be unique among Supabase-stored payment request records.
- `shareableLink` must include the unique hash.
- Backend validation must enforce every rule before inserting into Supabase.

State transitions:

```text
not created -> pending
```

No payment, withdrawal, fulfillment, expiration, or notification transitions are included in this feature.

## Storage Boundary

- Supabase stores `Payment Request` records generated by the system.
- Mock data remains the source of truth for `Demo User`, `Friend`, and `Receiver Account` records in this feature.
- Backend validation compares incoming request payloads against mock data before creating Supabase records.
